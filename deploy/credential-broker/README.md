# Opt-in synthetic credential broker

This is a standalone Docker boundary prototype, disconnected from T3 runtime and all production services. It cannot authenticate Codex or deploy to Cloudflare. It uses Node's standard library and the same pinned Node 26 base as the restricted runner. No package install is required.

Run explicitly from a trusted Docker host (Python 3 and Docker required):

```sh
TMPDIR=/home/grr/Projects/ro/work/privacy-tmp python3 deploy/credential-broker/test-docker.py
```

The test builds a uniquely tagged image, creates two internal networks and three disposable containers, generates only a synthetic credential, and removes its containers, networks, image and temporary credential on normal completion or test failure. It does not publish ports, change Docker context, use real tokens, or configure production connections. An abrupt host termination can leave resources named `broker-test-<random>`; remove only the resources belonging to that interrupted run. Docker may retain build cache containing source code, never the generated credential. Never provide a real secret: the broker requires both `BROKER_SYNTHETIC_ONLY=1` and a `synthetic-<64 hex>` credential fixture. These are accidental-use guards, not a security classification system.

The trusted controller uses `docker exec` to call `127.0.0.1:8081` inside the broker. `POST /leases` accepts exactly `{"scope":"fixture.ping","ttlMs":30000}` (TTL 1–30000 ms) and returns a random 256-bit bearer token. `POST /revoke` accepts exactly `{"token":"..."}`. The controller has Docker privileges; it is not an agent-accessible API. No admin socket, credential mount, PID namespace or engine socket is shared with the workload. Workload and upstream are on separate internal networks; the broker joins both.

The workload calls `POST http://broker:8080/operate` with exactly `{"scope":"fixture.ping","lease":"..."}`. This triggers only `POST http://upstream:8080/fixture/ping`, with an empty body and broker-injected Authorization. Caller URLs, paths, commands, additional body fields, and Authorization/Proxy-Authorization headers are rejected. Other headers are never copied upstream. Node's HTTP client does not follow redirects. Only an upstream 204 yields `{"ok":true}`; upstream headers and bodies are discarded, and errors are fixed strings. This intentionally cannot proxy arbitrary provider traffic.

Leases expire against a monotonic clock, are revocable, and allow one attempt. Consumption precedes asynchronous I/O, so concurrent replay has one winner and an upstream failure still spends the lease. Restart clears every lease. Revocation and expiry prevent future admission; they cannot undo an already admitted operation. Leases are hashed in memory, capped at 256 live records, and expired records are swept on issuance. A lease is an operation capability, **not** the raw provider credential and **not** an attested workload identity. Possession permits use until consumed, revoked or expired. The controller must establish identity and authorization before handing one out.

## Boundary and limitations

The isolation claim applies only to the unprivileged workload container in this launcher: no mounts, read-only root, no capabilities, no privilege escalation, limited resources, private PID namespace, no Docker socket. The test probes missing credential paths, a denied mount, denied upstream access by name and IP, and inaccessible admin TCP port. This is evidence for this configuration, not proof against kernel/container vulnerabilities or a hostile Docker administrator. The host user running this test can read the synthetic host file and use Docker to inspect broker memory/files. File permissions do not isolate a same-user host agent. A real agent must actually execute inside the restricted workload; merely routing one tool through it is insufficient.

Broker code, image, DNS/network topology, upstream, controller, Docker daemon and host administrator are trusted. Bootstrap credential provisioning remains operator-managed. HTTP is acceptable only for this isolated synthetic fixture: no TLS, SPIFFE/SVID verification, per-workload cryptographic binding, durable audit, distributed revocation, encrypted storage, key rotation or production egress policy is implemented. Leases can be stolen and raced by another process in the workload. Availability attacks and timing/status side channels remain. V8 string memory is not deterministically zeroed or locked. Only fixed startup messages are logged; tests check observed logs/errors, not every possible runtime failure. The upstream necessarily receives the credential.

## Smallest future integration seam

Keep identity verification, grant policy, operation execution and secret storage separate. A future trusted controller should verify a workload identity, authorize a fixed operation for an explicit target, and deliver a short lease into that workload. A broker-owned credential provider could expose `withCredential(fixedHandle, operationCallback)`, resolving storage only inside the broker; it must not expose a resolver to the workload. The callback itself must remain trusted, fixed code, never caller-supplied code. Storage-backend identity and bootstrap credentials stay at that trusted boundary.

The read-only Eidos `broker-endpoint.ts` and `eidos-broker/lease.ts` informed this callback/lease shape. Their HMAC/length fixtures do not supply a T3 provider deployment adapter, and a Unix socket scoped to the same host user is not container isolation. No Eidos code is imported. Timestore and Infisical are possible future implementations of storage resolution; neither is wired, validated, migrated to, or claimed secure by this prototype.

For T3/Cloudflare, the next bounded adapter should execute one approved deployment action for an operator-fixed account/project and artifact digest, with a fixed HTTPS endpoint/method, strict request schema, safe result projection, redirect refusal and enforced egress. T3 passes only that action and the workload lease, never a provider token. Identity verification, approval policy, credential provisioning and integration tests against the actual provider API are still required. Codex authentication needs its own explicitly supported protocol adapter; this fixed HTTP fixture does not establish one. Do not add an arbitrary URL/header proxy or hand the credential to a provider CLI in the workload as a shortcut.
